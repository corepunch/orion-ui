# Independent 1C report reconciliation

Use this procedure for [#348](https://github.com/corepunch/orion-ui/issues/348).
A staged XML generated by Ledger is **not** an independent 1C control. Keep the
original snapshot read-only and outside the repository. For each reconciliation
capture the following from the same snapshot and organization:

1. Generate the native report in 1C and export the original XLSX or MXL. Save
   the configuration/platform version, date range, organization/INN, currency,
   report filters, and report settings. Keep the original export alongside the
   normalized reference.
2. Import the snapshot into a disposable Ledger infobase and export the
   corresponding Ledger report. Save the Ledger revision and the same filter
   settings. Do not copy rows from the reference to fill Ledger gaps.
3. Independently normalize the two exports to the selected schema below.
   Export **UTF-8 comma-separated CSV**, with the exact header shown. Preserve
   identifiers as text, including leading zeros. Remove display-only subtotals
   unless explicitly selecting only totals in both reports. Select the same
   grain (for example, monthly by account or annual by account) on both sides.
   Enter money as signed minor units in the one currency specified in the
   manifest: write 123.45 RUB as `12345`, not a decimal or spreadsheet float.
   Use source GUIDs or a documented shared identifier mapping, not display
   names. Preserve cancellation, correction and additional-sheet rows.
4. Record the SHA-256 of the source `.1CD` and both
   normalized CSVs in a job manifest. Preserve the original exported reports
   as evidence; their format and layout depend on the 1C configuration and are
   not guessed by the tool.

| Profile | CSV columns |
| --- | --- |
| `trial-balance` (ОСВ) | `account,subaccount,opening_debit,opening_credit,debit,credit,closing_debit,closing_credit` |
| `payroll` (начисления, выплаты, НДФЛ) | `month,person,accrued,paid,withheld` |
| `contributions` (страховые взносы) | `month,person,contribution,source_document,amount` |
| `depreciation` (амортизация) | `month,asset,expense_account,opening,additions,depreciation,disposals,closing` |
| `vat-book` (книги НДС) | `quarter,book,invoice,event,sheet,source_line,rate,net,vat,gross` |
| `entities` (организации и связанные записи) | `kind,source_id,target_id,organization_tax_id,owner_id` |
| `attachments` (внешний файловый том) | `file_guid,owner_guid,owner_type,volume_guid,bytes,sha256` |

Use `YYYY-MM` for month and `YYYY-QN` (for example `2026-Q1`) for quarter.
In VAT books, use `purchase` or `sales`; keep rate, event, sheet and source
line as explicit identities, even if the corresponding net balances cancel.
Record whether NDFL is recognized by payout date in the manifest. A blank
subaccount, expense account or owner ID is allowed where those fields do not
apply; unobserved amounts are not zeros. An empty report is not verification.

Manifest example (replace the hash placeholders before running):

```json
{
  "format": "ledger-1c-reconciliation-v1",
  "profile": "trial-balance",
  "organization": "Test company, INN 0000000000",
  "period_start": "2025-01-01",
  "period_end": "2025-12-31",
  "source_report": "Оборотно-сальдовая ведомость",
  "source_version": "platform 8.3.x; configuration 3.0.x",
  "ledger_version": "exact Git revision",
  "settings": "RUB; annual by account/subaccount; no filters",
  "snapshot_sha256": "<SHA-256 of the 1CD>",
  "reference_sha256": "<SHA-256 of normalized native report>",
  "ledger_sha256": "<SHA-256 of normalized Ledger result>"
}
```

```sh
python3 apps/ledger/tools/reconcile_1c.py trial-balance \
  --manifest job.json --snapshot /reference/1Cv8.1CD \
  --reference /reference/1c.csv --ledger /disposable/ledger.csv > result.json
```

Exit 0 means all normalized identities and values matched. Exit 1 reports
each missing identity or differing field. Exit 2 means invalid or unverifiable
inputs, including malformed headers, duplicate keys, period mismatch, changed
files, or empty rows. The tool changes no inputs and prints monetary differences as exact integer strings
so JSON clients cannot round large values. Results are private accounting data.

For a real **external volume**, first import the source copy through the
snapshot-bound import manifest. Export the payloads from Ledger after closing
and reopening the infobase. Compare them with an independently exported copy
from 1C, not the bytes used to create a synthetic manifest. Put the two sets in
separate directories as `<canonical-file-guid>.bin` and pass them using
`--reference-payloads` and `--ledger-payloads`. Each payload must match its
listed size and SHA-256; source file GUID, owner, type and volume are compared
separately. Repeat on a second Ledger export after a repeat import without the
volume and check that the earlier file survived.

The included tests generate their own controls. They do not prove parity
against native 1C reports or a real external filesystem volume; those remain
required evidence before closing #348.
