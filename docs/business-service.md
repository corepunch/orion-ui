# Общий сервер Ledger и Lodge

На 12 ноября 2026 года целевой первый сегмент — небольшая торговая компания
и небольшой отель, Россия и Германия. Поддерживаются локальная работа владельца
и общий сервер бизнес-команд. HTTP API и командный клиент уже реализованы;
обычные окна Ledger/Lodge пока открывают локальную базу, а не этот HTTP API.
Наличие сервера не означает готовности удалённого графического рабочего места.

## Границы архитектуры

Локальный режим использует существующие `.orion`, модели и XML-хранилище с одним
писателем, резервной копией и миграциями. Сервер запускает эти же предметные
механизмы в отдельном процессе, без окна: `orion-service` для декларативных
приложений и `ledger-run --request` для Ledger. Клиент передаёт данные команды;
имя исполняемого файла, пути, Lua-модуль, роль и исполнитель не приходят из сети.

Один сервер обслуживает одну компанию. Для второй компании или другой страны
нужен отдельный каталог состояния и экземпляр сервера. Нельзя одновременно
использовать серверный каталог как локальную базу или общую сетевую папку.

На каждый запрос сервер:

1. Проверяет случайный токен и назначенную ему роль, затем разрешение команды.
2. Проверяет сохранённую квитанцию по паре «пользователь, request_id».
3. Сверяет `expected_revision` с текущей версией и SHA-256 активной базы.
4. Копирует базу в изолированный рабочий каталог и запускает доверенный host.
5. Проверяет результат и синхронизирует файлы новой версии.
6. Одной транзакцией SQLite публикует ссылку на новую версию, квитанцию запроса
   и запись журнала. До неё рабочая копия не видна другим пользователям.

Процессы одной компании сериализуются. Две брони из одного устаревшего состояния
не смогут одновременно опубликоваться: второй клиент получит конфликт версии,
обновит данные и снова пройдёт проверку доступности номера. Это начальная модель
для небольшого бизнеса; здесь нет параллельных пишущих транзакций или кластерной
доступности. Хранить рабочий каталог следует на локальном диске сервера.

Сбой связи после фиксации не требует нового платежа: повторяется **тот же**
`request_id` и весь исходный запрос, включая старую `expected_revision`.
Квитанция возвращается до проверки устаревшей версии. Изменение параметров
с прежним ключом отклоняется. После осознанного исправления отказанного запроса
клиент создаёт новый ключ. Тот же принцип используется в гостиничном журнале
оплат через отдельный `request_key`.

Квитанции успешного чтения также сохраняются. При смене роли прежние права
не сохраняются: разрешение проверяется до возврата квитанции.

## Запуск

Сборка использует имеющиеся зависимости проекта и стандартную библиотеку Python:

```sh
make share build/bin/orion-service build/bin/ledger-run
python3 tools/orion_server.py init --state /tmp/hotel-de \
  --application lodge --country DE \
  --executable build/bin/orion-service --resources apps/lodge/share
python3 tools/orion_server.py user --state /tmp/hotel-de \
  --user reception-1 --role reception
python3 tools/orion_server.py serve --state /tmp/hotel-de
```

Команда `user` выводит новый секрет один раз. Сохранить его нужно в защищённом
хранилище рабочего места. В `users.json` остаётся только SHA-256 высокоэнтропийного
секрета, идентификатор и роль. Повторная команда для того же пользователя меняет
токен; `--revoke` отзывает его. Изменение действует для следующих запросов,
в том числе при работающем сервере. Уже допущенная команда может завершиться.
Не используйте произвольные короткие пароли вместо создаваемых токенов.

Для бухгалтерии:

```sh
python3 tools/orion_server.py init --state /tmp/trade-ru \
  --application ledger --country RU \
  --executable build/bin/ledger-run --resources apps/ledger/share
```

RU выбирает `ru-2026`, DE — `de-2026`. `--configuration` позволяет оператору
явно выбрать конфигурацию; поддержка конкретного учёта определяется самой
конфигурацией и [аудитом Ledger](../apps/ledger/docs/compliance-readiness.md).
Для переноса собственной закрытой локальной базы можно добавить `--source DIR`.
Исходная база должна быть закрыта: копирование работающего каталога не является
согласованным экспортом. Источник не изменяется. Инициализация выполняет миграцию
и проверку приложения до создания `READY`; незавершённый экземпляр не запускается.

Для Lodge страна устанавливает пару DE/EUR или RU/RUB. При импорте старых данных
это **явное принятие единицы существующих сумм**, без пересчёта валюты. Перед
импортом оператор обязан знать, в какой валюте велись старые суммы. Настройка
не выбирает налоговую ставку и не превращает расчёт в налоговый счёт-фактуру.

Без сертификата сервер слушает только loopback. Для доступа по сети:

```sh
python3 tools/orion_server.py serve --state /srv/orion/hotel-de \
  --bind 0.0.0.0 --port 8790 --cert /etc/orion/server.pem --key /etc/orion/server.key
```

Нужен сертификат, доверенный клиентам. Минимальная версия TLS — 1.2. Клиент
проверяет сертификат; переключателя отключения проверки нет. За сервером должны
быть настроены учётная запись ОС, резервное копирование, ограничение доступной
сети и дисковые квоты. Внешнюю публикацию сервера эта инструкция не выполняет.

## Клиент и контракт версии 1

Токен передаётся через переменную окружения `ORION_TOKEN`, не в URL и не в
аргументах процесса:

```sh
python3 tools/orion_client.py --url http://127.0.0.1:8790 status
python3 tools/orion_client.py --url http://127.0.0.1:8790 request booking.json
```

`booking.json`:

```json
{
  "request_id": "booking-2026-001",
  "expected_revision": 4,
  "command": "reserve",
  "args": {
    "room_id": 1, "guest_id": 1,
    "arrival": "2026-12-01", "departure": "2026-12-03",
    "persons": 2, "rate": 80, "extras": 0, "notes": ""
  }
}
```

Сначала создаются номер и гость (`save_room`, `save_guest`). Уборка подтверждает
готовность номера перед заселением. Число `4` в примере нужно заменить версией
своего сервера, полученной после предыдущей операции. Клиент не делает скрытого
повтора с новой версией: это могло бы незаметно изменить смысл операции.

- `GET /v1/status`: версия протокола, приложение, страна, версия данных.
- `POST /v1/command`: ровно `request_id`, `expected_revision`, `command`, `args`.
- Успех: `ok`, `result`, `revision`, `request_id`.
- Предметный отказ: `ok:false`, `error`, неизменившаяся `revision`.
- HTTP 401/403 — авторизация; 409 — конфликт версии или ключа; 502/503/504 —
  обработчик, хранилище или таймаут. При неопределённом результате повторяется
  сохранённый запрос, а не новая операция.

Актуальный проверяемый список команд и ролей — `POLICIES` в
[orion_server.py](../tools/orion_server.py); повторная проверка предметных прав —
в `apps/lodge/share/service.lua` и `apps/ledger/share/service.lua`.

| Приложение | Роль | Основные возможности |
|---|---|---|
| Lodge | admin | Настройки, рабочие операции, закрытие дня |
| Lodge | reception | Гости, номера, брони и группы, тарифы, оплаты, заезд/выезд |
| Lodge | housekeeping | Только номера и состояния уборки; без гостей и сумм |
| Lodge | auditor | Чтение операций и просмотр дня |
| Ledger | admin | Торговые операции и закрытие периода |
| Ledger | accountant | Справочники, создание/правка черновика, проведение, сторно |
| Ledger | auditor | Чтение справочников, документов и журнала |

Это фиксированные начальные роли. Делегирование произвольных разрешений,
многофакторный вход и интеграция с корпоративным IdP пока отсутствуют.

## Сохранность, журнал и ограничения

Хранятся активная и предыдущая версии файлов, квитанции и журнал действий.
Журнал связывает строки хешами и содержит исполнителя, команду, результат,
время UTC и версию. Он не содержит тела запроса. Для защиты от администратора
самого сервера нужен внешний неизменяемый журнал: текущая цепочка не доказывает,
что владелец файлов не переписал или не обрезал её целиком.

Авторизация общего [API баз данных](database-access.md) дополнительно
проверяет нативные сообщения и Lua. Доверенные C-модули и владелец файлов
остаются внутри границы доверия. В серверном процессе не включается внешний
`ORION_PLUGIN_ROOT`; новая версия обработчиков устанавливается оператором после
проверки. Подпись пакета сама по себе не изолирует произвольный нативный код.

Текущие инженерные ограничения:

- Один снимок до 32 MiB, рабочая копия с резервными файлами до 64 MiB,
  до 4096 файлов/каталогов, вложенность до 16.
- Запрос до 1 MiB, ответ/вывод обработчика до 4 MiB, до 120 секунд на команду;
  16 одновременных сетевых соединений, 15 секунд на чтение запроса.
- Вывод дочернего процесса ограничивается при чтении. Рабочий каталог проверяется
  во время исполнения; это не замена жёсткой квоте файловой системы.
- Квитанции и журнал растут; оператор контролирует размер `state.sqlite`.
  Автоматического удаления квитанций нет, чтобы не потерять защиту повторов.
- Определение гостиничного операционного дня использует часовой пояс процесса
  сервера. Его нужно настроить по месту отеля; страна не определяет часовой пояс.
- Внешние платежи, фискализация и отправка отчётности не участвуют в транзакции
  снимков. Таких сетевых побочных действий данные обработчики не выполняют.
- Windows-код требует отдельного запуска в Windows CI. Локальная проверка
  macOS не подтверждает Windows/Linux развёртывание.

Резервное копирование и проверка: [эксплуатация сервера](server-operations.md).
Проверки: `make business-server-check` — JSON, шлюз с внедрёнными сбоями,
авторизация, конкурентные запросы, резервные копии и настоящие предметные hosts.

Сервер дополнительно отделяет гостиничные ключи оплаты по пользователю:
в предметный host передаётся `server:` + SHA-256 от пары пользователя и исходного
`request_key`. Поэтому одинаковые локальные ключи двух рабочих мест не подменяют
чужую оплату. Ключ нельзя повторно использовать для другой суммы или брони;
это проверяет сам журнал Lodge. Для нового платежа нужен новый ключ, для повтора
того же платежа — прежний. Локальные оконные оплаты используют своё пространство
ключей. Headless host также заменяет actor/role JSON-конверта значениями своей
доверенной сессии перед вызовом прикладного обработчика.
